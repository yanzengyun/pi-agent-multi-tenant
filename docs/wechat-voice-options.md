# 微信语音回复的后续方案

调研日期：2026-10-14。本文是方案与证据记录，未部署新通道或播放页面。

## 当前结论

当前女声 MP3 附件已被用户实际收到。原生 SILK、pi-connect 原样 AMR、补齐编码与时长的 AMR 均没有在用户微信显示气泡。两轮 AMR 的 API 接受与客户端失败记录在 `scripts/voice-probe/`。不能把接口成功当作客户端送达，也不能据此断言所有微信通道永久不支持语音。

本轮从 npm registry 读取官方包最新版本 `2.4.10`，直接检查发布 tarball 内的 `src/messaging/send-media.ts`：仍只有视频、图片和文件路由，音频进入文件分支。因此升级官方插件本身没有找到可解决气泡的新增实现。

官方仓库 [issue 209](https://github.com/Tencent/openclaw-weixin/issues/209) 报告同环境曾成功、后来手机和电脑均收不到原生语音；[issue 290 的 2026-10-03 用户反馈](https://github.com/Tencent/openclaw-weixin/issues/290) 也区分文字正常与 VOICE 不呈现。这些是用户报告，不是腾讯确认根因。现象倾向通道投递能力或限制问题，仍不能确定发生在服务端还是客户端。

## 路径一：保留现有微信，增加网页播放链接

这是减少手动下载步骤的最小改动方案，不是原生语音气泡，也未进行微信手机端验收。

计划沿用现有 MiniMax 女声合成，生成一段音频并保存到有期限的私有记录；微信回复包含“点击播放”链接。用户在微信内打开页面，点击播放按钮，浏览器读取 MP3，无需用户手动保存附件。移动浏览器通常需要点击才能开始播放，不能承诺打开即自动播放。

可复用现有 Node 服务和 HTTPS 网关，不需要额外容器、模型或 GPU。播放记录固定所属用户与运行，使用不可猜测、短期有效、可撤销的访问令牌。令牌只授权这一段音频，页面不开放聊天、记忆、配置或其他用户记录。音频过期清理；支持 Range 与正确 MIME，关闭缓存和跨站引用泄漏，日志不记录访问令牌。链接持有人在期限内可播放，应明确这是有期限的分享链接。

网关必须给播放路径独立配置访问方式，不能触发现有全站 Basic 验证弹窗，也不能放开管理后台。手机必须信任 HTTPS 证书；必要时使用域名与受信证书。验收包含真实微信内打开/点击播放、跨用户不可列举、过期与撤销、原主账号与 Lucy 文字/MP3 仍正常。

## 路径二：增加官方微信客服通道

腾讯 [微信客服发送消息文档](https://developer.work.weixin.qq.com/document/path/94677) 明确提供 `msgtype=voice` 与 `voice.media_id`。素材通过 [上传临时素材](https://developer.work.weixin.qq.com/document/path/90253) 获取；语音要求 AMR、不超过 2MB 与 60 秒。现有独立 AMR 编码器可以复用，失败的 iLink 上传和发送协议不沿用。

官方文档限制：用户主动发消息后，48 小时内最多回复 5 条；用户再次发消息可刷新。还需要客户处于允许 API 回复的接待状态，应用获得对应客服账号的接口权限。API 接受仍不保证最终送达，要处理发送失败事件。不能用这一通道承诺无条件定时提醒。

开源参考 [CowAgent 的微信客服适配器](https://github.com/zhayujie/CowAgent/blob/master/channel/wechat_kf/wechat_kf_channel.py) 包含实际 AMR 转码、voice 素材上传和 `kf/send_msg` 发送路径；这证明存在可参考的完整实现，不代表我们自己的账户已通过真机验收。

部署需要企业微信中的微信客服账号、可调用接口的应用、独立凭据与回调加密配置、公网 HTTPS 回调和客服入口链接。用户仍在微信内聊天，但进入新的客服会话，不能把当前 ClawBot 会话原地变成微信客服。

建议先做隔离的一句话女声 AMR 试验：配置一个测试客服入口，用户发消息，后端合成/上传/发送，用户确认气泡和播放；成功后再接 Pi 后端。现有用户 UUID、人物设定、记忆、笔记与 trace 可以复用，不再建一套 Pi 或 SB。新增 `(channel, account_id, external_userid) -> user_id` 绑定，通过本人登录或一次性确认绑定已有用户，不能按昵称自动合并账户。微信客服的 external_userid 不等于现有 iLink remote_user。

接入后每轮处理回执、文字与语音都计算发送额度，避免工具执行进度刷屏；主动提醒继续走现有通道，并分别展示各通道状态。回调去重、同步 cursor、接待状态、失败事件与重试需单独实现。

## 路径三：继续 iLink 原生实验

只有找到新的可复现客户端成功案例，或腾讯公布明确支持条件，才值得再次按证据测试。验收必须包含真实客户端显示和播放，不能只看 SDK 的 `SendVoice` 方法或 README 勾选。

本轮检查 `1ncludeSteven/weixin-sdk-go` 的 HEAD 源码，`pkg/messaging/send.go` 使用 VOICE 上传、raw-key base64 与 playtime，未设置 encode_type；未找到相应手机成功验证。它是另一种载荷实现，不是已验证的修复。其他公开排查已尝试 raw/hex AES key 与用户入站载荷复现，因此不把换 SDK 或重复改字段作为优先方案。

[Gewechat 当前 README](https://github.com/Devo919/Gewechat) 明确停止维护且不再提供历史服务或镜像。历史 `postVoice` 文档不能作为当前可部署成功方案，不替换现有登录。

## 建议

优先网页播放链接改善当前微信的听音体验；若原生气泡是硬要求，先准备微信客服账号做隔离真机验证。保留现有 MP3 与正常生产服务，验证成功后再决定新增通道。
